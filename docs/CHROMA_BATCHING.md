# ChromaDB 요청 크기 초과 복구

`Batch size ... exceeds maximum batch size ...`는 임베딩 계산과 별개인 DB 요청 크기
제한입니다. 19,517개를 최대 5,461개인 환경에서 한 번에 저장하면 발생합니다.
`embedding.batch_size`는 모델 연산의 묶음 크기이며 이 저장 제한을 해결하지 않습니다.
HNSW의 batch_size도 저장 API의 요청 제한과 다른 설정입니다.

공통 PersistentChromaStore는 client.get_max_batch_size()로 현재 백엔드의 허용 수를
확인하고 upsert 및 ID 기반 조회/삭제를 나눠 실행합니다. 제한이 5,461이면 19,517개는
5,461 + 5,461 + 5,461 + 3,134로 나눕니다. 코드와 문서 인덱서 모두 같은 저장 계층을
사용합니다. 배치 간 ID·본문·임베딩·메타데이터의 대응 관계를 유지합니다.

모든 입력의 ID/차원/중복을 먼저 검사하고 저장합니다. 중간 배치가 실패하면 성공으로
반환하지 않고 원래 예외를 cause로 유지합니다. 여러 요청 전체가 하나의 원자적
트랜잭션은 아니므로 앞선 배치는 남을 수 있습니다. 같은 ID의 upsert 재시도로 수렴합니다.

수정 버전을 적용한 뒤:

- CLI 색인은 기존 설정과 상태 파일을 유지하고 실패한 색인 명령을 다시 실행합니다.
- API 등록 문서는 기존 실패 작업을 현재 버전으로 재시도합니다. 화면의 실패 작업
  재시도 또는 `/v1/ingestion/{namespace}/documents/{id}/retry`를 사용합니다.
- 이 오류 때문에 기존 Chroma DB를 삭제하거나 원본 문서를 다시 분할할 필요는 없습니다.

현재 패키지 요구 조건인 Chroma >=1.5,<2의 클라이언트 API를 사용합니다. 실행 환경의
허용 수가 유효한 양의 정수가 아니면 무제한 쓰기로 우회하지 않고 오류를 반환합니다.

검증은 정확히 19,517개/최대 5,461개의 요청 분할, 항목 대응, 대량 조회/삭제,
중간 실패 후 재시도와 입력 선검증을 포함합니다. 실 Chroma에서도 작은 제한을 주입해
여러 배치의 저장·조회·삭제를 확인합니다. 실제 임베딩 모델은 이 저장 테스트에 필요 없습니다.
